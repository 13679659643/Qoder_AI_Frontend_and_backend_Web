# Power BI 常见踩坑与避坑指南

> 面向 Power BI 日常开发与问题排查，重点覆盖 DAX、数据模型、矩阵、切片器、Power Query、性能、刷新和安全。
> 使用方式：先查「现象速查表」，再看对应编号；每条围绕「现象 → 原因 → 推荐做法 → 验证」展开。
> 适用边界：通用机制与 RL E2E 项目口径分开描述。本文仅新增知识文档，不修改现有报表、模型、业务口径或历史文件。
> 验证状态：已进行资料核对与静态检查；示例未连接实际 Power BI 模型运行，应用时必须替换字段并完成文末测试。

## 二、DAX：最容易算错的 19 个点

### 01. 把计算列、计算表当成随切片器变化的度量值

- **现象**：用 DAX 建了一张客户分层表，切换日期后分层没有变化。
- **原因**：Import 模型中的计算列、计算表通常在模型刷新或重新处理时计算并存储；度量值在查询时根据当前筛选上下文计算。
- **推荐**：需要跟随日期、门店、平台交互的结果写成度量值；稳定分类、排序字段等才考虑列或辅助表。
- **验证**：分别执行「切换切片器」与「刷新模型」，观察结果在哪一步变化。

| 对象                           | 数据刷新后可变化       | 随当前切片器重新计算表达式 | 典型用途                   |
| ------------------------------ | ---------------------- | -------------------------- | -------------------------- |
| Power Query 列 / Import 计算列 | 是                     | 否                         | 清洗、稳定属性、关联键     |
| DAX 计算表                     | 是，取决于表达式依赖   | 否                         | 日期表、参数表、刷新时快照 |
| 度量值                         | 查询时读取当前模型数据 | 是                         | 金额、占比、动态排名       |

`DATATABLE` 的数据区用于声明常量；`UNION + ROW` 可以引用表达式，但创建为计算表后依然不会随页面切片器重新生成。已有计算表被筛选，与它的表达式重新计算，是两回事。

### 02. 混淆行上下文、筛选上下文与上下文转换

- 矩阵某一行对度量值施加的是**筛选上下文**，不是 DAX 迭代器的行上下文。
- `SUMX`、`FILTER`、`ADDCOLUMNS` 的逐行计算会创建行上下文，但普通 `SUM` 不会自动按该迭代行筛选事实表。
- `CALCULATE` 可以把行上下文转换为筛选上下文；在行上下文中引用模型度量值时，会自动发生上下文转换。

以下为表达式片段，假设 `Dim_Store` 通过有效的 1:N 关系筛选 `Fact_Sales`：

```dax
// 错误意图：想按门店分别求金额，但裸 SUM 没有使用迭代行的门店筛选。
SUMX(VALUES(Dim_Store[StoreKey]), SUM(Fact_Sales[Amount]))

// 正确表达该意图：对每家门店执行上下文转换。
SUMX(VALUES(Dim_Store[StoreKey]), CALCULATE(SUM(Fact_Sales[Amount])))

// 如果 [Sales Amount] 已定义为 SUM(Fact_Sales[Amount])，也可以这样写。
SUMX(VALUES(Dim_Store[StoreKey]), [Sales Amount])
```

**验证**：两家门店金额分别为 10、20 时，第一个表达式可能得到 60，后两个为 30。本例只是解释机制；单纯求总金额直接用 `SUM` 即可，不必额外迭代。

### 03. VAR 缓存的是结果，不是可在新上下文重新执行的公式

```dax
// 错误意图：__Sales 已在原上下文中求值，清除门店后不会重新计算。
VAR __Sales = [Sales Amount]
RETURN
    CALCULATE(__Sales, REMOVEFILTERS(Dim_Store))

// 正确意图：把需要重新求值的度量值放在 CALCULATE 内。
VAR __AllStoreSales =
    CALCULATE([Sales Amount], REMOVEFILTERS(Dim_Store))
RETURN
    __AllStoreSales
```

- **边界**：VAR 可以保存标量，也可以保存表。表变量同样保留定义位置的求值结果，外层换筛选不会自动重建它。
- **验证**：逐店比较当前销售额与全店销售额，后者应符合预先确定的分母范围。

### 04. 误以为 CALCULATE 总是追加筛选，且参数从左到右执行

假设当前切片器直接筛选 `Dim_Product[Color] = "Blue"`：

| 表达式                                                                 | 含义                 | 结果范围               |
| ---------------------------------------------------------------------- | -------------------- | ---------------------- |
| `CALCULATE([Sales Amount], Dim_Product[Color] = "Red")`              | 替换同列筛选         | 红色产品               |
| `CALCULATE([Sales Amount], KEEPFILTERS(Dim_Product[Color] = "Red"))` | 与已有同列筛选取交集 | 红与蓝无交集，通常为空 |

- 同级筛选参数不是顺序执行的 SQL 脚本；不能认为前面的 `REMOVEFILTERS` 会先影响后面的 `VALUES`。
- 例如 `CALCULATE([Sales Amount], REMOVEFILTERS(Dim_Store), VALUES(Dim_Store[StoreKey]))` 中，`VALUES` 仍可能取到原上下文的当前店，再把它筛回去。
- **推荐**：先说明要「替换」还是「取交集」。确实需要分阶段求值时，用明确的嵌套 `CALCULATE/CALCULATETABLE`，不要依赖参数排列。
- **验证**：分别测试原筛选与新增条件相同、相斥、多选三种情况。

### 05. ALL、REMOVEFILTERS、ALLSELECTED 用错，或漏掉排序列

| 工具              | 主要用途                                 | 常见误解                                   |
| ----------------- | ---------------------------------------- | ------------------------------------------ |
| `REMOVEFILTERS` | 在计算中清除指定列/表的普通筛选          | 不能作为`FILTER` 的表输入                |
| `ALL`           | 可返回表，也可作为清除筛选的修饰符       | 清整张事实表的影响可能比想象更广           |
| `ALLSELECTED`   | 常用于保留外部选择、计算视觉范围内的合计 | 不等于在任何位置都能得到「屏幕可见行之和」 |
| `KEEPFILTERS`   | 把新增筛选与已有同列筛选取交集           | 不会帮你选择业务分母                       |

先回答分母是什么：全集团、当前平台全部门店、当前所选门店、当前父分类，还是当前 Top N？这些不是同一个数。

```dax
Sales Share Selected Store =
// ========================================
// 中文名：所选门店销售额占比
// Display Folder：示例/占比
// 用途：当前门店金额 ÷ 外部所选门店总金额。
// 依赖：[Sales Amount]；Dim_Store[StoreName]、Dim_Store[Store_Sort]。
// 口径：单层门店矩阵，保留日期、平台及外部门店选择。
// 与错误写法差异：同时处理视觉查询中可能携带的门店排序列。
// ========================================
    VAR __Numerator = [Sales Amount]
    VAR __Denominator =
        CALCULATE(
            [Sales Amount],
            ALLSELECTED(Dim_Store[StoreName], Dim_Store[Store_Sort])
        )
    RETURN
        DIVIDE(__Numerator, __Denominator)
// 验证：仅选择 A、B，金额 30、70 时，占比分别为 30%、70%。
// 边界：多层矩阵须重新定义父层保留范围；不能直接推广为任意层级模板。
```

- 配置「按列排序」后，查询可能同时携带显示列和排序列；只移除显示列时，排序列可能让分母仍停留在当前行。
- 可以同时处理相关列；若业务允许，也可对整个行维度使用 `ALLSELECTED`，但要检查是否改变父层或其他属性范围。
- 同表多列筛选还可能受 auto-exist 的已有组合合并影响；`ALL` 不是重新生成不存在组合的工具。
- **验证**：把分母单独放进矩阵；切换排序配置、父层、小计、Top N 与外部切片器后再检查。

### 06. SELECTEDVALUE 返回 BLANK，不一定是没选

`SELECTEDVALUE(列, 备选值)` 在当前上下文恰好有一个不同值时返回该值；否则返回备选值。默认备选值为 `BLANK()`。

| 当前上下文     | 默认返回 | 能否据此断言「没有选择」 |
| -------------- | -------- | ------------------------ |
| 一个非空值 A   | A        | 否                       |
| 唯一值本身为空 | BLANK    | 否                       |
| 多个不同值     | BLANK    | 否                       |
| 没有可见值     | BLANK    | 否                       |

- **推荐**：读单选参数用 `SELECTEDVALUE`；检查单值用 `HASONEVALUE`；传递多选集合用 `VALUES`；需要排查时同时输出 `COUNTROWS(VALUES(...))`。
- **注意**：把备选值设成 `"ALL"` 会让多选、无有效值等情况也进入 ALL 分支，只有明确允许时才这样做。
- `MAX` 虽然能消除「不能确定单个值」报错，却可能把多选静默变成最大值。

### 07. 用 BLANK 或 HASONEVALUE 判断层级，而不是 ISINSCOPE

对于普通的「区域 → 门店」逐级展开矩阵：

| 所在位置                   | `ISINSCOPE(区域)` | `ISINSCOPE(门店)` | 应使用逻辑 |
| -------------------------- | ------------------- | ------------------- | ---------- |
| 区域下的门店明细           | TRUE                | TRUE                | 门店级     |
| 区域小计                   | TRUE                | FALSE               | 区域级     |
| 总计                       | FALSE               | FALSE               | 总计级     |
| 总计，但切片器仅选一家门店 | FALSE               | FALSE               | 仍是总计级 |

- **推荐**：`SWITCH(TRUE(), ISINSCOPE(最深层), ..., ISINSCOPE(上层), ..., 总计)`，从深到浅判断。
- `HASONEVALUE(门店)` 在最后一行情形可以为 TRUE，但并不代表当前是门店明细。
- 真实空成员也可以处在明细层，不能因 `SELECTEDVALUE(...)` 为空而放行整列。
- **边界**：该真值表针对上述展开布局；「转到下一级」、字段参数换层、多字段平铺后，必须重验实际 scope。

### 08. BLANK、0、空字符串不是同一种业务含义

- `BLANK()` 可以表示缺数据、无适用口径、分母无效或刻意隐藏；0 表示有效计算结果为零。
- 普通比较 `=` 可能发生空值强制转换，例如 `BLANK() = 0` 为 TRUE；严格比较 `==` 不把二者视为相同。
- 判空优先用 `ISBLANK`；不要把 `= BLANK()` 当作通用精确判空。
- `COALESCE([Value], 0)` 会改变无数据行列的显示与统计含义，不能为了「好看」到处加。
- **验证**：分别准备有记录金额为零、完全无记录、文本空串三种数据；不要只看格式化后的屏幕显示。

### 09. DIVIDE 已处理除零，后面的减 1 又制造了 -100%

```dax
// 风险片段：DIVIDE 返回 BLANK 后，继续参与减法可能得到 -1。
DIVIDE([Current Sales], [Prior Sales]) - 1
```

下面示例明确采用「本期缺数据不当作零；同期为零或缺失时不计算增长率」的口径：

```dax
Sales Growth % =
// ========================================
// 中文名：销售额增长率
// Display Folder：示例/增长率
// 依赖：[Current Sales]、[Prior Sales]。
// 口径：真实零销售可比较；缺数据不转零；同期零值不计算。
// 与错误写法差异：先检查边界，再进行减法和除法。
// ========================================
    VAR __Current = [Current Sales]
    VAR __Prior = [Prior Sales]
    RETURN
        IF(
            ISBLANK(__Current) || ISBLANK(__Prior) || __Prior == 0,
            BLANK(),
            DIVIDE(__Current - __Prior, __Prior)
        )
// 验证：0 对 100 为 -100%；BLANK 对 100 为空；100 对 0 为空。
```

| 本期  | 同期  | 本例返回 |
| ----- | ----- | -------- |
| 120   | 100   | 20%      |
| 0     | 100   | -100%    |
| BLANK | 100   | BLANK    |
| 100   | 0     | BLANK    |
| 100   | BLANK | BLANK    |
| 0     | 0     | BLANK    |

**边界**：若业务明确「无记录等于零」，应在指定层统一转换；同期为负数时，是否使用原值、绝对值或不展示，必须另定口径。纯差值也要检查 BLANK，不能只检查除法。

### 10. 总计不是把屏幕上的比率、平均值再相加

| 门店 | 销售额 | 订单数 | 每订单金额 |
| ---- | ------ | ------ | ---------- |
| A    | 100    | 1      | 100        |
| B    | 900    | 3      | 300        |
| 总计 | 1,000  | 4      | 250        |

- 正确总计为 `DIVIDE([Sales Amount], [Order Count]) = 250`，不是 400，也不是简单平均 200。
- Power BI 通常在总计上下文重新计算度量值；只有业务明确要求「逐行结果之和」时，才选择适当粒度使用 `SUMX`。
- 「所有门店平均客单价」与「所有订单平均金额」可以是两个不同 KPI，不能凭名称判断。
- **验证**：用数量差异明显的两组数据手算；数量相同的例子容易掩盖错误。

### 11. FORMAT 把数值变成文本，百分比、pts、bp 又容易重复缩放

- `FORMAT` 返回文本；后续数值排序、数值轴、聚合和条件格式可能不再按预期工作。
- **推荐**：基础值、比较值保持数值；优先设置格式字符串或动态格式字符串。自定义矩阵确需拼接时，独立建立 `Cell Display`。
- `FORMAT(0.25, "0.0%")` 已显示 25.0%，不要先乘 100 再用百分比格式。

以占比从 20% 变为 25% 为例：

| 指标       | 计算                    | 结果   |
| ---------- | ----------------------- | ------ |
| 相对增长率 | `25% / 20% - 1`       | 25%    |
| 百分点差   | `(25% - 20%) * 100`   | 5 pts  |
| 基点差     | `(25% - 20%) * 10000` | 500 bp |

金额先除以 1,000，再配置视觉对象显示单位为「千」，会重复缩放。汇率还要明确报价方向、日期粒度及缺失处理，不能用最大汇率代替最新汇率。

### 12. IF / SWITCH 不能用来返回动态表分支

```dax
// 错误意图：IF 不是表选择器，分支列数一致也不能解决。
VAR __Rows = IF(__UseA, __TableA, __TableB)
```

同一张源表按模式筛选时，使用表函数承载结果，把条件放进谓词。以下为度量值内部片段，`__Mode` 是已读取的标量参数：

```dax
VAR __Users =
    DISTINCT(
        SELECTCOLUMNS(
            FILTER(
                Fact_CustomerMonth,
                (__Mode = "New" && Fact_CustomerMonth[IsNew] = 1)
                    || (__Mode = "Retention" && Fact_CustomerMonth[IsRetention] = 1)
            ),
            "UserKey", Fact_CustomerMonth[UserKey]
        )
    )
```

- 已有两个表集合时，可以使用互斥条件的 `UNION(FILTER(__TableA, __UseA), FILTER(__TableB, NOT(__UseA)))`；先确保列数、列序和类型对应，需要时再 `DISTINCT`。
- `IF` 放在 `FILTER` 内返回 TRUE/FALSE 是合法的；`IF(条件, COUNTROWS(表A), COUNTROWS(表B))` 也是合法标量表达式。
- **边界**：上述片段继承当前筛选；它本身不负责建立业务时间范围。度量值最终还必须返回标量。

### 13. TREATAS 传的是指定列集合，不是整套筛选上下文

- 两张事实表不因都有 `UserKey`、`StoreKey` 就自动互相筛选。
- `TREATAS(用户集合, Fact_Order[UserKey])` 只传递用户限制，不会顺便传递会员状态、日期、商品等筛选。
- 多列映射按位置对应，列数与语义必须一致；不存在于目标列的值会被忽略。
- 多列组合应整体传递，例如「门店＋用户」集合不能拆成独立的门店列表与用户列表，否则会额外允许交叉组合。
- **推荐**：稳定公共维度优先建关系；确需虚拟关系时写明源集合、目标键、列顺序以及是否使用 `KEEPFILTERS` 保留目标已有筛选。
- **验证**：测试一人跨店、源有目标无、空集合、空成员、复合键不同组合；空集合应表示没有匹配，而非放行全部。

### 14. DISTINCTCOUNT 不可随意相加，而且会统计 BLANK

- A 店客户为 `{U1, U2}`，B 店为 `{U2, U3}`；各店人数 2、2，总人数为 3，不是 4。
- `DISTINCTCOUNT` 会将 BLANK 计为一个不同值；无行时返回 BLANK。排除空客户键可使用 `DISTINCTCOUNTNOBLANK` 或明确筛掉空键。
- `VALUES` 在某些关系完整性问题下可能包含额外未知成员，不能不加检查地把它当纯净客户名单。
- **推荐**：先定义统计单位是用户、用户＋店铺、订单还是请求；跨月、跨店合计按目标粒度重新去重。
- **验证**：刻意加入跨组重复用户和空用户键，再对照去重明细列表。

### 15. 先圈人、再统计的 Step1 + Step2 被压成一次聚合

以 RL E2E VIC Breakdown 的特定口径为例：

| 步骤  | 回答的问题                              | 时间范围               |
| ----- | --------------------------------------- | ---------------------- |
| Step1 | 结束财月中，哪些用户属于指定 VIC 人群？ | 结束财月               |
| Step2 | 这批用户在完整所选期间贡献多少？        | 所选开始财月至结束财月 |

- **推荐结构**：Step1 用 `CALCULATETABLE(VALUES(...), 圈人条件)` 得到主体集合；Step2 用 `CALCULATE(聚合, TREATAS(...), 统计期间条件)`。
- 两步分别核对身份、平台、门店、员工等条件；不能认为 Step1 的所有身份条件都要复制到 Step2，也不能认为都应移除。
- 若业务要求按行分组，Step2 不应随意清除相关行维度；只有需要全量分母的分支才按分母口径移除。
- **项目特定坑**：完整期间起点应来自起始月的 Min 表；从结束月 Max 表读取其周期自身起点，会退化为末期单月。
- **验证**：固定结束月只改开始月，圈人集合可保持不变，但历史金额应按数据变化。使用「期末满足资格、早期尚未满足资格却有交易」的用户做反例。
- **边界**：这不是 DAX 禁止合并表达式；而是未经等价证明的合并会改变业务定义。新客等其他 KPI 的 Step1/Step2 顺序和时间语义可能不同。

### 16. 清了事实日期，却没清日期维度；自然月又被当成财月

- 日期维度仍筛着本期时，仅清除事实表日期列未必能算出同期；两个日期限制可能交集为空。
- 使用自定义区间时，先取得区间标量，再在计算中替换正确的日期筛选。若还保留年份、月份筛选，要确认它们不会与新日期范围冲突。
- 普通自然月偏移不等于企业 4-4-5 财历、53 周财年或自定义 LP；优先使用经过确认的财历区间映射。
- 「截至今天」不等于「截至数据已完整的最后一天」；本期未完整时，不应直接与完整同期比较。
- **验证**：跨年、闰日、非连续选择、财年边界、起点大于终点，以及本期缺数据的情况。

### 17. 字符串类型与匹配范围没想清楚

- `SWITCH` 比较 STRING 列时使用字符串分支，如 `"1"`；不要为了匹配而随意 `VALUE` 转换 ID，可能丢前导零或遇到非数字报错。
- `CONTAINSSTRING("TMALL", "TM")` 为 TRUE；它是包含匹配，不是完整字段相等。
- 平台、状态、指标 ID 等枚举值优先使用 `=` 或 `IN`；确实存多值标签时，应按规范拆分或建桥接表，避免子串碰撞。
- `CONTAINSSTRING` 还支持通配符；实际业务文本中的 `*`、`?` 不能都按普通字符理解。
- **验证**：加入 `TM`、`TMALL`、`01`、`1`、空值及带空格数据；明确哪些必须区分。

### 18. 「按组取最新」与「先聚合再判断」都依赖正确粒度

- `MAX(PushTime)` 只得到时间；用时间等于最大值过滤，遇到并列时间可能保留多行。
- `MAX(ExchangeRate)` 得到最大汇率，不等于最新记录的汇率。
- 先筛选「成功」再取最新，会得到「最新一次成功」，不等于「最新记录是否成功」。
- `SUM(金额) > 0` 不等于先筛掉金额非正的记录再求和；退款记录会让结果明显不同。
- **推荐**：声明分组键、时间键、并列时第二排序键；需要唯一行时，使用确定性排序与唯一键，不能把 `TOPN(1)` 无条件当成只返回一行。
- **验证**：同一业务键构造两条不同时间、两条同时间、成功后失败、正向销售后退款等记录。

### 19. 排名范围只剩当前行，或 Top N 的比较集合前后变化

- 在矩阵当前商品行直接对 `VALUES(商品)` 排名，候选集可能只剩一个商品，导致每行都排第 1。
- 明确排名是在全量商品、当前父分类、外部所选商品还是当前期间有数据的商品中进行，再选择筛选移除范围。
- `RANKX` 的 Dense/Skip 决定并列后的名次；按「排名 <= N」或 `TOPN` 筛选都可能因并列返回超过 N 项。
- 同比比较还要区分「各期自己的全部成员」与「本期成员回看历史」。先拿本期事实表组合筛到同期，会排除仅同期存在的成员。
- **验证**：包含并列值、仅同期有数据的品牌、只在下级出现差异的组合，并比较展开/折叠后的统计范围。

## 三、数据模型：5 个基础不牢就全盘算错的点

### 20. 没定义事实表粒度，就开始 SUM / COUNTROWS

- **现象**：订单金额、月目标、库存被重复累计。
- **原因**：订单头金额重复在商品明细上；月目标关联到每天；每日库存跨日期相加；不同汇总层级混在同一张表。
- **推荐**：每张事实表先写一句「一行代表什么」，确定业务唯一键；不同粒度分别建模，汇总层标记明确过滤。
- **验证**：抽一张多商品订单、一项月目标、连续三天库存，分别核对订单数、金额和期末值。
- **边界**：库存通常可跨门店相加，却不可跨日期直接相加；期末快照还须定义取公共截止日还是各实体最后有效日。

### 21. 维度键不唯一、事实外键缺失，关系却只看线连上了

- 维度侧键必须符合关系的唯一性要求；显示名称通常不适合作为跨系统主键。
- 空键、尾部空格、类型不一致、重复键和未匹配键，会造成空白成员、漏数或关系无法按预期建立。
- **推荐**：在数据源或 Power Query 中检查维度唯一键与事实孤立键，并决定未知成员的业务处理；不要为修报错就改成多对多。
- **验证**：维度总行数与唯一键数对比；用反连接找出事实表中不在维度表的键。

### 22. 用双向关系或事实表直连解决所有筛选问题

- 默认优先共享维度向事实表的单向 1:N 星型结构；双向和多对多不是语法错误，但必须有明确需求与验证。
- 双向路径可能导致筛选绕行、维度选项被意外裁剪、总计改变，并增加安全传播与性能复杂度。
- 同一日期对订单日期、发货日期可能有不同关系角色；需要按发货日期统计时，检查是否应使用 `USERELATIONSHIP` 或独立角色日期维度。
- **验证**：画出每个切片器到每张事实表的传播路径，并逐表放置简单计数度量验证。不要只验证一张事实表。

### 23. 日期只改了显示格式，底层仍带时间

- `2025-01-01 12:00:00` 与日期维度的 `2025-01-01 00:00:00` 不是同一个关系键；显示成「2025-01-01」不会截断时间。
- **推荐**：在源端或 Power Query 生成 Date 类型关联键，原始时间戳另行保留；先统一业务时区，再确定日期。
- 使用共享、连续、无空值且日期唯一的日期维度；经典日期列时间智能按要求标记日期表，避免多个自动日期表各算各的。
- 自定义日历功能与经典时间智能的要求可能不同，不能照搬一套设置。
- **验证**：检查正午和午夜记录、跨时区午夜记录，以及报表页是否混用事实日期与日期维度字段。

### 24. 主键精度、文本大小写与小数误差被忽视

| 风险                               | 推荐做法                                                               |
| ---------------------------------- | ---------------------------------------------------------------------- |
| 长 ID 经 Excel/浮点数转换后丢位    | 源头保护精度；优先文本业务键或合适的整数代理键，丢位后再转文本无法恢复 |
| `00123` 被转成 `123`           | 标识符按业务决定是否保持文本，别当可运算数字                           |
| 金额浮点误差影响相等比较或排名     | 明确精度；适合时用固定小数类型或在业务规定的位置 ROUND                 |
| SQL 区分大小写，而模型去重语义不同 | 校对源端排序规则与模型行为；需要区分的实体使用稳定代理键               |
| 汇总前四舍五入与汇总后四舍五入不同 | 写入 KPI 口径与验收用例                                                |

**边界**：不要笼统地说「所有 DAX 文本函数都不区分大小写」；如 `EXACT` 有特定比较语义。导入时已合并或丢失的键差异，无法靠后续函数凭空恢复。

## 四、矩阵与切片器：4 个看起来像 DAX、实际是交互或显示的问题

### 25. 断开参数表没有关系，必须由度量值读取并映射

- 指标列头、币种、计算模式等参数表可以刻意不建关系，但选中某项不代表事实表会自动被筛选。
- **推荐**：单选模式读取 `SELECTEDVALUE` 后路由 `SWITCH`；多选使用集合映射。明确 `"ALL"` 是哪几种实际值，不等于自动涵盖所有源数据。
- 稳定行维度优先复用模型关系，不要仅因使用中国式矩阵就把所有维度都断开。
- 参数表的 `IsDefault = TRUE` 只是普通数据，不会自动把切片器设置为默认选中；仍需报表默认状态、书签或度量值兜底逻辑。
- **验证**：单选、多选、清除选择、选择已无数据项；同时确认标题与数值使用同一套选择规则。

### 26. 行可见性度量不能简单改字段就变成列可见性筛选器

- 原生矩阵的视觉对象级度量筛选，其评估粒度由 Rows 字段决定，不能假设列字段也按单元格方式参与该筛选粒度。
- 但**矩阵单元格里的度量值**可以取得当前列筛选；不能把筛选器的限制推广成「SELECTEDVALUE 永远读不到列」。
- 需要隐藏全空列时，先确保业务值及最终显示值在应隐藏处返回真正 `BLANK()`，关闭「显示无数据的项」，并检查值区域的其他度量是否撑住了列。
- `0`、`"-"`、空占位图片 URL 都不能替代应隐藏位置的 `BLANK()`；也不应依赖空字符串作为稳定的隐藏机制。
- **验证**：仅保留基础数值度量，逐步加回 Display、SVG 与其他指标，找出哪个返回值让空列保留。
- **边界**：展开层级、Top N、字段参数和多度量布局都会改变结果；换视觉对象类型后要重新验证筛选粒度。

### 27. SVG 的灰色占位仍是非空值，需要分清「交叉点空」与「整行列空」

假设单层热力矩阵的基础值如下；「—」仅用于表示 BLANK，不是实际返回文本：

| 行 / 列 | X  | Y  | Z  |
| ------- | -- | -- | -- |
| A       | 10 | — | — |
| B       | — | 20 | — |
| C       | — | — | — |

若需求为「保留有效行列交叉处的灰色占位，隐藏全空行列」：

| 交叉点 | 当前 Value | 所在行有非空 Value | 所在列有非空 Value | SVG 应返回   |
| ------ | ---------- | ------------------ | ------------------ | ------------ |
| A × X | 10         | 是                 | 是                 | 数值 SVG     |
| A × Y | BLANK      | 是                 | 是                 | 灰色占位 SVG |
| B × X | BLANK      | 是                 | 是                 | 灰色占位 SVG |
| A × Z | BLANK      | 是                 | 否                 | 真正的 BLANK |
| C × X | BLANK      | 否                 | 是                 | 真正的 BLANK |
| C × Z | BLANK      | 否                 | 否                 | 真正的 BLANK |

- 行/列有效性应检查基础 Value，不要检查已带占位的 Display/SVG，否则会循环证明「处处有值」。
- 行检查只放宽列轴的相关约束；列检查只放宽行轴的相关约束，并按需求保留日期、平台和外部选择。排序列和多级轴同样需要考虑。
- 两个 `ISINSCOPE` 只能识别是否处于行列明细，不会自动判断该行或列是否有数据。
- 真实数值 0 在「非空即有效」口径下仍有效；若要排除零，应另定规则。
- **验证**：最终应只保留 A、B 行和 X、Y 列，两个空交叉点显示占位。不能承诺所有矩阵布局直接套用同一段可见性代码。

### 28. 排序、书签、同步切片器与交互设置让页面悄悄变口径

- 「按列排序」要求同一个显示值对应一个排序值；只用月份名称跨年排序无法表达完整年月顺序。
- 自定义参数表创建了 `_Sort`，还要在模型中设置显示列按该列排序。本项目常用 10、20、30 的间隔，这是项目约定，不是 Power BI 强制要求。
- 书签若保存「数据」状态，切换布局时可能一并恢复旧筛选；仅切换外观时检查书签捕获范围。
- 同步切片器即使在某页隐藏，也可能继续筛选；交叉高亮与交叉筛选的统计效果不完全相同。
- **验证**：重置报表、切书签、钻取、跨页返回、切用户视图，并检查页面/视觉/报表三级筛选和「编辑交互」。

## 五、Power Query 与刷新：4 个常见数据加工坑

### 29. 自动类型识别、区域设置与错误吞掉数据

- 日期文本 `01/02/2025` 的月日解释取决于区域设置；小数点、千分位、编码也会导致类型转换差异。
- `try ... otherwise null` 可以避免刷新中断，但会把转换失败隐藏成缺失值，不能当成数据已经修好。
- **推荐**：关键列显式设置类型和区域；保留错误标记与异常行数量，避免静默删除整行或统一转零。
- **验证**：查看整列数据质量而非只看预览样本；加入异常日期、超长 ID、空文本和非数字金额。

### 30. Merge 展开让一行变多行，Distinct 又掩盖了根因

- Left Join 只保证保留左表记录，不保证展开后左表行数不增加；右表一个键有两行，左侧金额就可能复制两遍。
- **推荐**：合并前验证右表匹配键唯一性；确有多对多明细时设计正确粒度，不要直接累计重复的头金额。
- 不要盲目使用「删除重复项」修复金额翻倍，也不要依赖排序后 `Table.Distinct` 必然保留某一条最新记录；需要确定性选行规则。
- **验证**：记录合并前后行数、业务键数、金额总和以及未匹配数量；任何变化都要能解释。

### 31. 把查询折叠和 Table.Buffer 当成固定口诀

- 能否折叠取决于连接器、源系统、变换表达式及组合方式；不能说「所有自定义列/逆透视/引用查询都一定不能折叠」。
- 「查看本机查询」可用时有助于检查下推 SQL；菜单不可用不一定等于完全没折叠，也可能是连接器不提供该查看能力。
- **推荐**：尽早筛行、选列；使用可用的本机查询、查询诊断或源端查询记录核验实际取数。Power Query Online 可结合折叠指示器与查询计划。
- `Table.Buffer` 可能增加内存和耗时，并阻止后续折叠；它不是通用加速开关。
- **验证**：比较刷新耗时、源端扫描/返回行数和请求次数。引用一个查询不代表它只被执行一次或有全局缓存。

### 32. 增量刷新边界重复，或历史更正落在窗口外

以下是接在已有 `Source` 步骤后的 M 示例；`OrderDateTime` 和两个参数均为 Date/Time 类型：

```powerquery
let
    // 半开区间：边界记录只进入一个分区。
    Filtered = Table.SelectRows(
        Source,
        each [OrderDateTime] >= RangeStart
            and [OrderDateTime] < RangeEnd
    )
in
    Filtered
```

- `RangeStart`、`RangeEnd` 参数名区分大小写；Desktop 的样本范围不等于 Service 中的正式分区策略。
- `>= 起点、< 终点` 是常用约定；`> 起点、<= 终点` 也能保持不重叠。不能同时两端都含等号，否则相邻分区可能重复收录边界记录。
- 大数据量场景必须核验区间条件有效下推；本地分区筛选但每次仍扫描全源，可能严重拖慢或导致刷新失败。
- 刷新窗口外的历史修改不会因「开启增量」自动重算；退款、补单、删除和迟到数据需有回补策略。
- **验证**：插入恰等于边界的记录，修改窗口内外各一条历史记录，再检查哪些分区更新。首次 Service 刷新通常比后续重，不要拿首次耗时代表日常耗时。

## 六、性能、发布与安全：8 个上线后才暴露的点

### 33. 只凭函数名字判断性能，不看扫描粒度与查询计划

- `SUMX` 不一定慢，`FILTER` 也不是禁用项；真正要看迭代行数、嵌套次数、上下文转换、存储引擎下推和每格重复计算。
- 简单列条件优先直接布尔筛选；复杂跨行/跨表逻辑再用适当表表达式，不能为性能改写而改变语义。
- 行列全部组合、逐格 SVG、多个重复度量与全事实表扫描可能放大查询成本。
- **验证**：Performance Analyzer 定位慢视觉；DAX Studio 在可用时分析 Server Timings/查询计划；VertiPaq Analyzer 查看高基数列与模型体积。
- 优化前后保持相同筛选、结果与测试条件，分别记录冷/热缓存耗时；没有测量就不要宣称提升了多少。

### 34. DirectQuery 不等于零延迟实时，Import 也不是永远更合适

- DirectQuery 查询依赖数据源，但仍受视觉刷新、缓存、网关和源端延迟影响，不保证每秒自动看到最新数据。
- Import 交互通常更稳定，但可见数据受模型刷新时点限制；Dual/复合模型需要理解跨存储模式的查询路径。
- 部分 DAX 函数在 DirectQuery 计算列、RLS 中受限制，不代表同函数在所有度量值场景都不可用。
- **推荐**：根据实时性、数据规模、源端承载和功能限制选模式，不要只因「数据量大」就直接切换 DirectQuery。
- **验证**：修改一条测试源数据，分别触发视觉刷新、模型刷新，记录什么时候真正可见。

### 35. Desktop 能连，不代表 Service 的网关环境也能连

- Service 不会使用开发电脑当前的本地磁盘、驱动、用户 DSN 和登录状态。
- ODBC 等连接需检查网关主机的驱动版本与位数、适用的 DSN、服务账号可见性、网络可达性及数据源映射。
- **推荐**：用参数区分开发/测试/生产端点；凭据放入受管理的连接或凭据配置，避免嵌入 M/SQL。
- **验证**：发布后立即执行一次 Service 手动刷新，检查刷新历史和失败步骤；再验证计划刷新，不以 Desktop 成功代替上线验收。

### 36. 把「刷新完成时间」当成「业务数据完整时间」

- 模型刚刷新成功，不代表源数据包含今天；源端可能仍只产出前一天或某张表延迟。
- `MAX(日期维度[日期])` 可能是未来日历日期，不能证明事实数据已到该日；事实表最大日期也不保证当日已完整。
- Desktop 本地时间、Service UTC 和业务时区可能不同；计算列中的 `TODAY/NOW` 也不会随报表每次打开而自动重新处理。
- **推荐**：分别标注模型刷新时间、业务数据截止时间，重要场景使用源系统完成标志或水位表。
- **验证**：让一张事实表故意落后一天，确认多表 KPI 不会悄悄混用不同数据截止日。

### 37. RLS 不是页面隐藏，也不约束所有工作区角色

> **安全提醒：RLS、工作区权限与分享方式必须人工复核，并使用真实受限身份验收。**

- 隐藏页面、隐藏字段、遮罩按钮、返回 BLANK 的度量值都不是数据权限隔离。
- 在工作区中，RLS 适用于 Viewer；Admin、Member、Contributor 具有编辑权限，不按普通 Viewer 的 RLS 方式受限。
- 一个用户属于多个 RLS 角色时，通常是授权结果叠加，而不是自动取最小权限交集。
- `ALL/REMOVEFILTERS` 只能清除普通计算筛选，不能绕过模型已施加的 RLS；若管理员看到全量，先检查身份权限而不是怪这两个函数。
- **验证**：用不同受限用户测试直接访问、应用访问、导出和 Analyze in Excel 等已授权通道；检查无匹配身份、多个角色与组织外用户。

### 38. 凭据、PBIX 与「发布到 Web」被误当普通分享材料

- 不在文档、M、SQL、截图或提交历史中保存真实密码、Token、API Key。发现泄露后应轮换凭据，单纯删除当前文件不足以消除历史泄露。
- PBIX 可能包含导入的数据；「隐藏字段」不会从文件中移除数据，也不等于脱敏。
- 「发布到 Web」属于公开发布，不适合任何敏感或受限报表，不等于向指定同事分享。
- **验证**：发布前审查连接配置、截图、导出权限和文件分发范围。测试样本仅使用合成或脱敏数据。

### 39. SQL 对账只比一个总数，没统一去重、时间和过滤语义

- 在常见 SQL 方言中，`COUNT(DISTINCT 列)` 排除 NULL；DAX `DISTINCTCOUNT` 包含 BLANK，不能直接认定两个数应该相同。
- 对齐同一数据快照、业务键、时区、区间边界、会员/员工条件、平台范围、退款规则和最新记录逻辑。
- 总计一致可能掩盖分类互相串数；分类一致也可能掩盖跨分类去重总计错误。
- **推荐**：先对账原始金额/人数，再对账比率，最后检查 Display；至少保留总计、典型明细、交叉重复和异常数据四类证据。
- **验证**：差异时输出具体业务键集合，用交集/差集找原因，不只反复改聚合函数。

### 40. 修改基础值后，Display、条件颜色与口径文档没有同步

- 基础度量改了单位或 BLANK 规则，Display 可能仍重复缩放，颜色可能仍把空值当零，总计分支可能仍执行旧口径。
- 金额换币不一定影响占比和计数；不能对一整个矩阵所有指标统一套汇率。
- **推荐**：按「数据源 → 基础值 → 同期值 → 差值/比率 → Display → 颜色/SVG → 可见性」检查依赖链，记录受影响的 KPI 与页面。
- **验证**：改动后回归所有相关指标路由、层级与边界分支；业务口径、示例结果和实现保持一致，保留可追溯变更记录。

### 复用旧笔记时，避免把经验口诀当成语言限制

| 常见说法                               | 更准确的理解                                                                               |
| -------------------------------------- | ------------------------------------------------------------------------------------------ |
| 「EARLIER 不能用于度量值」             | 它要求可用的外层行上下文；度量值内部也可以有嵌套迭代。本项目优先 VAR，不代表语言绝对禁止。 |
| 「LASTDATE 是标量函数」                | 它返回表表达式；部分上下文可发生标量转换，不应据此混淆返回类型。                           |
| 「IF 两分支表结构相同就能返回表」      | 不成立。用 FILTER/SELECTCOLUMNS/UNION 等表函数构造集合，IF 负责标量条件。                  |
| 「维度表一加上，所有空交叉格一定显示」 | 还取决于查询生成的组合、关系、度量值和无数据项设置，不能脱离视觉查询保证。                 |
| 「所有行维度都应断开」                 | 仅参数/特殊展示映射等场景按需断开，稳定业务维度优先关系传播。                              |
| 「按列排序后 ALLSELECTED 必须清整表」  | 应覆盖实际残留的分组/排序筛选；整表与显式列集要按父层、外部选择及业务范围决定。            |
| 「看不到本机查询就说明完全不折叠」     | 查看能力与折叠能力不同；需结合连接器和实际请求验证。                                       |
| 「SUMMARIZE 会自动只留每组最新一条」   | 分组不等于确定性选行；仍需最新时间、过滤顺序、并列处理与最终去重键。                       |
